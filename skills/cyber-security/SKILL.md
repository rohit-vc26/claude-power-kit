# /cyber-security — Application Security Playbook

Two reference bodies fused into one operational checklist. Run the
relevant section against any code touching the surface listed, before
calling the work "done".

---

## PART A — The 7 Vibe-Coded App Vulnerabilities (+ Bonus)

Apps built fast with LLMs and AI agents tend to ship functionality
without non-functional security primitives. These are the seven failure
modes that recur. Severity is the source guide's classification.

### 1. Server-Side Template Injection (SSTI) — CRITICAL
**Exploit.** AI-generated templates render friendly login errors (or
any user-facing string) by concatenating raw user input directly into
string-interpolation fields of rendering engines like EJS, Pug, or
Jinja, instead of passing variables safely as data parameters. The
template engine then executes attacker payloads as code.

**Prevention.**
- Never use raw string interpolation or evaluation logic (`eval()`
  or custom template rendering) on incoming request payloads.
- Utilize built-in contextual auto-escaping; pass raw values
  exclusively via secure, sandboxed parameters.

**Smell test when reviewing.** Look for `render(` / `compile(` /
template strings whose arguments include `req.body`, `req.query`,
`req.params` directly, with no intermediate validation or escaping.

### 2. Regular Expression Denial of Service (ReDoS) — CRITICAL
**Exploit.** Unoptimized regex generated by AI assistants collapses
under catastrophic backtracking when evaluated against intentionally
malformed strings, trapping the single-threaded Node.js event loop.
One request from one attacker freezes the whole process.

**Prevention.**
- Use standard, battle-tested validation suites (e.g. `validator.js`)
  instead of prompting an AI to construct custom lookahead regexes.
- Implement aggressive response timeouts on application processes
  and test regex with static-analysis analyzers.

**Smell test.** Any regex containing nested quantifiers, e.g.
`(a+)+`, `(.*)*`, `(a|aa)+`, especially around email/URL/whitespace
validation, on a hot pre-auth path.

### 3. Long Password DoS — CRITICAL
**Exploit.** Failing to cap input sizes before processing them under
computationally heavy cryptographic algorithms (bcrypt, scrypt,
Argon2) lets a single 10,000-character payload exhaust host CPU.

**Prevention.**
- Enforce a hard max length (e.g. 128 chars) at the **routing /
  validation layer**, *before* the request reaches the database or
  hashing module.
- Drop oversized request content via upstream middleware or proxy
  config (nginx `client_max_body_size`, API gateway body limits).

**Smell test.** Login or register handler hashes whatever it gets
with no `maxLength` upstream. Combine with rule 5 (`bcrypt` already
truncates at 72 bytes — but the CPU is spent before that).

### 4. AWS / Cloud Secret Leakage Client-Side — CRITICAL
**Exploit.** Using framework env-var prefixes improperly — appending
`NEXT_PUBLIC_`, `VITE_`, `REACT_APP_`, `EXPO_PUBLIC_`, `PUBLIC_` onto
**private** environment parameters — exposes AWS root credentials (or
any secret) directly inside the compiled public JS bundle. Anyone who
loads the page can grep them out.

**Prevention.**
- Restrict credential parameters strictly to runtime `.env` files and
  build-time server-only checks. Public-prefixed env vars are *for
  the browser* — they are not secrets.
- Use AWS IAM Roles, OIDC federation, or short-lived STS credentials
  rather than static root keys in codebases. Same principle for
  Stripe, OpenAI, Twilio, Anthropic, Postmark — server-side proxy,
  never browser-side.

**Smell test.** `grep -rE 'NEXT_PUBLIC|VITE_|REACT_APP_|EXPO_PUBLIC_'`
against `(SECRET|KEY|TOKEN|PASSWORD|PRIVATE)` matches. Open compiled
bundle (`.next/static`, `dist/`) and re-grep — the post-build artifact
is the ground truth.

### 5. NoSQL Injection — HIGH
**Exploit.** Accepting raw, un-sanitized JSON request objects directly
into MongoDB query logic. A login body like
`{ "email": "...", "password": {"$gt": ""} }` bypasses the string
comparison and signs the attacker into the first matching account.

**Prevention.**
- Enforce strict request schemas with schema validators (Zod, Joi,
  Valibot, Yup) so every queried field is guaranteed to be a plain
  string/number, not an object/array.
- Sanitize data fields using dedicated `mongo-sanitize` /
  `express-mongo-sanitize` plugins to strip `$`-prefixed and dotted
  keys before queries run.

**Smell test.** `User.findOne({ email: req.body.email, password:
req.body.password })` with no schema gate above it. Same pattern in
Mongoose `find`/`update` calls.

### 6. Clipboard Copy Attack (Pastejacking) — HIGH
**Exploit.** Malicious web code (or a compromised dependency)
manipulates the OS clipboard during a copy event, injecting
terminal-executable strings hidden behind innocent-looking code
blocks. The user pastes "the install command" and runs the attacker's
shell command instead.

**Prevention.**
- Ensure terminal setups use **Bracketed Paste Mode** so multi-line
  pasted content can be inspected before execution rather than
  auto-executed on newline.
- Build copy-to-clipboard UI using secure, programmatic mechanisms
  (`navigator.clipboard.writeText(KNOWN_STRING)`) instead of letting
  the browser copy raw DOM selections that could contain injected
  invisible content.

**Smell test.** `document.execCommand('copy')` on a user-selectable
block, or `oncopy` handlers that mutate `clipboardData`. Treat any
"copy this curl command" pattern as a sensitive surface.

### 7. Login Replay Attack — LOW
**Exploit.** Interception of plain transmission cookies / data blocks
in transit, allowing a third party to replay un-expired
authentications directly into the backend without ever cracking the
secret.

**Prevention.**
- Enforce continuous TLS/HTTPS end-to-end (HSTS, `Secure` cookies,
  no mixed content) to encrypt transit footprints natively.
- Integrate server nonces or time-based one-time tokens (TOTP) so
  individual transmission items expire automatically. Bind sessions
  to IP / device fingerprint where the threat model warrants it.

**Smell test.** Cookies set without `Secure; HttpOnly; SameSite`.
Sessions with multi-month TTL and no refresh-rotation. Auth tokens
in URL query strings.

### Bonus — The Single-Thread Guardrail
**The trap.** Node.js backends run on a single event-loop thread. An
unhandled error or blocking operation inside any pre-authentication
field crashes the app **globally**, taking every user down at once.

**Pro-Tip.** Always run production apps under a cluster manager like
**PM2**, or inside auto-scaling AWS ECS / Fargate / Kubernetes tasks.
If an un-vetted attack slips past your login validation and triggers a
crash, the process manager instantly forks a fresh worker thread,
preserving uptime while you fix the underlying code.

This pairs with rules 1–6 as the failure-domain shrinker: harden the
input layer, *and* make crashes survivable.

## PART B — Password Storage: Hashing, Salt, Pepper

### B.1 The two hard requirements
When storing passwords, two non-negotiables:
1. You can **prove** a submitted password matches the stored one.
2. An attacker who steals the store **cannot recover** the originals.

Cryptographic hashing satisfies both — but only when used with the
right algorithm, with salt, and ideally with pepper.

> Build rule: do **not** implement the construction yourself.
> Standard algorithms (Argon2, bcrypt, scrypt, PBKDF2) are battle-
> tested and ship salt support natively. Feed parameters in; let the
> library mix.

### B.2 Why a plain hash is not enough
A cryptographic hash is deterministic and one-way:
`MD5("Baeldung") = d58b26d9f7600672080ebf3851115e45`. Same input →
same output, every time. A one-character change avalanches the digest.

(MD5 is illustrative only — it is broken for password use. So is SHA-1
and unsalted SHA-256. Use a *password* hash, not a *file-integrity*
hash.)

#### Brute Force
If the hash can't be reversed, the attacker iterates candidate
passwords, hashing each and comparing:
```
hash("aaaaaaaa") → 3dbe00a1...  ❌
hash("aaaaaaab") → 2125ea8b...  ❌
...
hash("Baeldung") → d58b26d9...  ✅ match
```
Time-to-crack depends on (a) algorithm cost and (b) password
complexity. Password hash algorithms are *deliberately slow* to
penalize this loop. General-purpose hashes (MD5, SHA-256) are
deliberately *fast*, which is exactly why they are wrong here.

#### Rainbow Tables
The attacker's optimization: precompute every hash once, store it,
then look up stolen digests instantly. That precomputed map is a
rainbow table.

- Every 8-char alphanumeric password ≈ 2.18 × 10¹⁴ rows. Large but
  tractable on modern storage.
- Once built, cracking collapses from years → seconds. It is a DB
  lookup, not a CPU loop.
- Two users with the same hash share the same password — crack one,
  crack them all.

### B.3 Salting — defeats rainbow tables
**Salt = a random per-password value mixed in before hashing.**
Stored alongside the hash, in plaintext, in the DB. Public is fine —
its job is uniqueness, not secrecy.

```
algorithm HashPassword(password):
    salt   <- generateRandomString()        # ≥16 bytes, CSPRNG
    result <- hash(password + salt)
    return (result, salt)
```

Storage example — same password, different salts, different digests:
```
Password="Baeldung", Salt="123" → f78bc836...
Password="Baeldung", Salt="987" → 586eccfc...
```

Verification recomputes with the stored salt:
```
algorithm VerifyPassword(password, storedSalt, storedHash):
    newHash <- hash(password + storedSalt)
    return newHash == storedHash
```

**Why it kills rainbow tables.** The precomputed table now has to
cover *every password × every salt*. With a 64-bit salt, ~1.845 × 10¹⁹
rows per single password; ~4.028 × 10³³ rows for every 8-char
alphanumeric input. Storage-infeasible.

**What salting does NOT do.** It does not stop brute force against a
single hash. The attacker stole the salt too — they can still iterate
candidates against one user's hash. Salt forces them to attack each
user separately rather than crack the whole DB in one shot.

### B.4 Peppering — closes the gap salt leaves
**Pepper = a single shared secret value mixed in alongside the salt,
NOT stored in the DB.** Lives in application config / secrets manager
/ HSM — anywhere outside the password store. A DB-only breach leaks
hashes and salts; the pepper stays unknown.

```
const pepper <- "someRandomValue"          # ≥64-bit, stored OUT of DB

algorithm HashPassword(password):
    salt   <- generateRandomString()
    result <- hash(password + pepper + salt)
    return (result, salt)
```

Salt is still required — without it, two users with the same password
collide to the same hash (because pepper is constant).

**Attacker's view after a DB-only breach.** They see `hash` and
`salt`. Even if they reverse-engineer a single hash to e.g.
`"Baeldung987123"`, they know `123` is the salt — but they cannot tell
where the pepper ends and the password begins. With a sufficiently
large pepper (e.g. 64-bit), brute force becomes infeasible.

**Operational sharp edges.**
- **Pepper rotation is brutal.** You cannot change it without
  invalidating every stored hash → every user must reset their
  password. Plan rotation policy on day one.
- **Pepper compromise = total loss.** Unlike per-user salts, one
  leaked pepper weakens every account simultaneously. Treat it like
  a private key: HSM/KMS, restricted access, audited reads.
- **Library support is uneven.** Argon2 supports pepper natively
  (its `secret` parameter). PBKDF2, bcrypt, scrypt do **not** — if
  you must use one of those, pre-HMAC the password with the pepper
  before feeding it to the KDF, and own the extra layer.

### B.5 Defaults
| Layer       | Stored where           | Per-user? | Defeats                       | Cost if compromised                |
|-------------|------------------------|-----------|-------------------------------|------------------------------------|
| Hash (KDF)  | DB                     | n/a       | Plaintext recovery            | n/a                                |
| Salt        | DB, plaintext          | Yes       | Rainbow tables, hash collisions | Low — attacker already had the DB |
| Pepper      | Outside DB (HSM/KMS)   | No (shared) | Brute force after DB-only leak | Catastrophic — forced full reset  |

**Default posture:**
- Algorithm: **Argon2id**. Fallback bcrypt (cost ≥12) or scrypt if
  Argon2 unavailable. PBKDF2 only when FIPS-required.
- Salt: ≥16 bytes from a CSPRNG, unique per password.
- Pepper: ≥32 bytes, stored in a secrets manager / HSM, *never* in
  git, *never* in the DB, *never* in client-shipped config.
- Length cap: hard max 128 chars at the validation layer (see A.3).
- Constant-time compare on the hash check.

## How to run this skill

When the user invokes `/cyber-security` (or any trigger above):

1. **Identify scope.** Ask which body applies, or infer:
   - Auth, login, register, password-reset code → Part B + A.3 + A.5 + A.7.
   - AI-generated controller / handler / validator → full Part A.
   - Frontend build / env config → A.4.
   - Regex / input validation → A.1 + A.2 + A.3.
   - Copy-to-clipboard UI / docs site → A.6.
2. **Read the target files** (Read / Grep / Glob). Do not paraphrase
   the rules from memory at the user — apply them to actual code.
3. **Report findings** as `(severity, rule #, file:line, evidence, fix)`.
   Each finding cites the rule it violates from this skill.
4. **Never silently auto-patch security code.** Present findings,
   wait for approval, then Edit.
5. **End with verification.** For Part B work, recommend a quick
   `argon2.verify()` round-trip test or equivalent. For Part A, run
   the smell-test greps and report empty matches as evidence.

- Stacks well with `/cso` (deeper threat modelling, STRIDE,
  dependency / CI-pipeline supply chain) — use `/cso` for monthly

  generation review.

### Hard rules
- Refuse to produce exploit weaponization beyond the smell-tests and
  defensive PoCs needed to verify a fix.
- Never write a real pepper, AWS key, or production secret to a file
  in this skill's output. Placeholders only.
- Never recommend MD5, SHA-1, unsalted SHA-256, or homegrown KDFs
  for password storage, even "just for the demo".
